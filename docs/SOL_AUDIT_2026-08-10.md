# Deckd Sol Audit, 2026-08-10

Scope: source and tracked web-export audit only. The reported 82 passing Jest tests were not rerun because this task permits no writes outside this report, and test tooling can create caches. Export sizes below were measured read-only from `app-serve/`.

Blunt verdict: the card engine and 375px web UI have useful foundations. Multiplayer recovery, online privacy, purchases, PWA offline support, and actual solo games are not ready to ship. The live build is a strong preview, not a dependable paid product.

## 1. Mobile multiplayer

### 1.1 [CRITICAL] There is no reconnect or room recovery

`RelayTransport` opens one WebSocket. `onclose` marks it closed and stops, with no retry, backoff, resume token, stable identity, network listener, heartbeat, or `AppState` handling (`lib/relayTransport.ts:91-126`). The lobby then deletes the session and roster (`src/store/lobbyStore.ts:76-92`). Every host/join also generates a fresh client ID (`src/store/lobbyStore.ts:52-54,104-160`).

A Wi-Fi to 4G switch, iOS suspension, process restart, or transient tunnel failure therefore ends that client's session. A guest cannot reclaim the same seat. A host disconnect is worse: the relay immediately closes and deletes the whole room (`server/index.js:201-213`). Mobile users experience a silent sync-chip disappearance, not recovery.

### 1.2 [CRITICAL] Disconnecting can expose the host's private hand to a guest

The close callback nulls `lobbySession` before the table's close effect checks `lobbyStatus === 'closed' && isOnline`. Since `isOnline` requires a non-null session, the redirect condition is false (`components/layers/TableLayer.tsx:111-126`). The viewer then falls back from the guest client ID to `state.meta.hostId` (`components/layers/TableLayer.tsx:128-141`).

The guest still has the persisted host event log, so after a dropped socket the UI can render from the host's viewpoint and permit local host actions. This is not merely stale UI, it is a private-hand leak and state fork.

### 1.3 [CRITICAL] Starting a second game in one lobby breaks broadcast sequencing

The bridge keeps one module-global `lastBroadcastSeq` and only sends events above it (`src/store/multiplayerBridge.ts:31-39,56-69`). Every new game resets its sequence to 1 (`src/store/gameStore.ts:133-172`), but production code never resets the bridge cursor. If game one ended at sequence 30, game two's start and first 29 events are suppressed. Existing guests remain on the old table until the new game happens to exceed 30, then receive contextless events. Current tests cover one session, not this lifecycle.

### 1.4 [CRITICAL] Online hand privacy is presentation-only

The host broadcasts the complete event chain to every guest (`src/store/multiplayerBridge.ts:72-84,200-205`). `session/start` includes every populated zone and card ID (`src/store/gameStore.ts:130-169`), while visibility is enforced only when selectors choose what to draw (`src/engine/state.ts:279-293`). On web, that full log is also persisted (`src/store/gameStore.ts:355-366`).

Any guest can inspect local storage or runtime state to read opponents' cards and deck order. Poker and blackjack cannot be called fair online until snapshots/events are filtered per recipient, with only public state plus that player's private hand sent to them.

### 1.5 [MAJOR] Delivery and latency handling are too weak

The transport silently drops a send when the socket is not open (`lib/relayTransport.ts:197-215`), while the bridge advances its cursor before attempting that send (`src/store/multiplayerBridge.ts:64-69`). There are no acknowledgements, retries, intent IDs, contiguous-sequence checks, or automatic resync. Guest folding sorts and deduplicates by ID but accepts sequence gaps (`src/store/syncLogic.ts:21-46`).

The `SYNCED` badge means only “socket connected” (`components/layers/TableLayer.tsx:522-527`). A guest action resolves immediately with no pending state (`components/layers/TableLayer.tsx:179-191`). If the host is suspended or a packet is lost during closure, tapping appears to do nothing and repeated taps can queue duplicate intents.

### 1.6 [MAJOR] A disconnected player can deadlock the turn

The game roster is copied once from the lobby roster (`components/layers/HubLayer.tsx:177-195`). Relay departures update only lobby membership, not game players or `currentPlayerId` (`server/index.js:162-174,201-213`). There is no reconnect-to-seat, kick, force-pass, bot takeover, or timeout. If the current guest disappears, the host can end the whole session but cannot safely advance that seat.

### 1.7 [MAJOR] The guest start flow is awkward and not state-driven

Every room member sees “Start the table” (`components/layers/LobbyLayer.tsx:242-292`). Host events update `gameStore` but never navigate the guest (`src/store/multiplayerBridge.ts:200-205`). The checked two-client script documents the real workaround: host starts/deals, then the guest separately taps Start, sees Resume, and taps Resume (`qa/deckd-lobby-two-client.cjs:78-93`). That is confusing on a phone and makes an accidental guest-created local table possible.

### 1.8 [NICE] The core authority model is salvageable, but the relay needs hardening

Guest actions are checked against known players, turn ownership, card ownership, and legal destinations on the host (`src/store/multiplayerBridge.ts:91-169`). Rooms cap at eight, refresh activity on relay traffic, and expire after six idle hours (`server/index.js:18-22,67-74,146-180,216`). Those are good bones. However, rooms live only in process memory, client IDs can overwrite map entries, protocol parsing is only a type assertion, and relay payloads have no size/rate limit (`server/index.js:135-188`; `lib/relayProtocol.ts:51-58`). A relay restart loses every room.

## 2. App Store and Mobile Safari

### 2.1 [CRITICAL] The web build is installable-looking, not offline PWA-ready

The manifest has a start URL, standalone display, colours, and icons (`public/manifest.webmanifest:1-14`). The HTML links it (`app/+html.tsx:21-32`). There is no service worker registration, precache manifest, offline fallback, update strategy, or install-state UX in the app shell. The static server merely reads files and falls back to `index.html` (`app-serve/serve.mjs:22-65`).

Result: an already-open tab can keep playing local pass-and-play, but a cold launch or reload without network is not dependable. Native installs can launch from their bundled assets; the live web app cannot honestly claim the same.

### 2.2 [MAJOR] iOS viewport, fullscreen, and keyboard handling are unfinished

The viewport omits `viewport-fit=cover`, and there are no Apple standalone/status-bar tags (`app/+html.tsx:15-32`). The generated shell uses a 100%-height, overflow-hidden root rather than a `100dvh`/visual-viewport strategy (`app-serve/index.html:1`). Safe-area hooks exist, but web safe-area values are weakened without `viewport-fit=cover`.

In Safari, browser chrome remains unless the user adds the app to Home Screen. Dynamic toolbars and the keyboard can clip absolutely positioned layers or bottom navigation. Test normal Safari, standalone PWA, landscape rejection, and text-input keyboard movement separately on a real iPhone.

### 2.3 [MAJOR] The mobile cold payload is fat and poorly served

The tracked export's single JS entry is 5,324,328 bytes raw and 988,473 bytes gzip. The full tracked `app-serve` payload is 7.23 MiB raw. Five font files are preloaded and the root blocks rendering on five fonts plus four image assets (`app/_layout.tsx:22-34,66-74`; `app-serve/index.html:377-381`). Three card-back PNGs alone are about 1.32 MiB.

The origin provides neither compression nor immutable hashed-asset caching, and sends `no-cache` for everything (`app-serve/serve.mjs:59-63`). Cloudflare may compress externally, but the origin configuration is still wasteful. Split routes, subset fonts, convert card backs to WebP/AVIF, serve Brotli/gzip, and cache hashed assets for a year.

### 2.4 [MAJOR] Native build configuration exists, but launch configuration and proof do not

This is a real Expo managed-app scaffold, not web-only: iOS/Android identifiers and build numbers exist (`app.json:11-32`), production EAS builds target App Store/AAB distribution (`eas.json:38-47`), and build/submit scripts exist (`package.json:13-16,27-28`).

It is not submission-ready. RevenueCat keys are empty (`app.json:33-36`), submit metadata is blank (`eas.json:49-57`), products are not configured, and no physical native device pass has been completed (`STATUS.md:70-78`). Blank credentials should stay out of Git, but EAS/ASC setup, signed builds, privacy declarations, screenshots, review notes, purchase sandbox tests, and device evidence still need doing.

### 2.5 [MAJOR] Store-facing capability copy is stale and risky

The iOS plist claims QR scanning and screenshot saving (`app.json:15-23`), but those flows are absent. Settings still says Bluetooth is the primary offline mode and may request permission (`app/settings.tsx:49-75`), while BLE is explicitly dropped from v1 (`STATUS.md:80-83`). Remove unused permission copy and rewrite settings before review. Shipping contradictory claims is sloppy and invites review questions.

### 2.6 [MINOR] 375px geometry is good, tap compliance is inconsistent

Browser QA reports 375×812 bounds and key controls at 44px+ (`STATUS.md:60-65`). Many explicit controls are sound, such as 48px nav items (`components/GlobalNavBar.tsx:374-388`) and 58px setup tokens (`components/layers/HubLayer.tsx:1206-1217`). However, generic small `CardButton` has only 8px vertical padding and no 44px minimum (`components/CardButton.tsx:135-149`), so header, copy, restore, and small pass buttons are not guaranteed to meet the target. Native touch remains untested.

### 2.7 [MINOR] Audio has no Safari bug because audio has no product

`expo-audio` is installed and configured (`package.json:31-44`; `app.json:41-46`) but nothing imports or uses it. There is therefore no user-gesture unlock, interruption recovery, mute preference, or background handling to audit. Remove it to reduce native surface area, or implement audio only from explicit taps and resume its session after `AppState` interruptions.

## 3. Monetisation

Overall score: 2/10. The shop looks designed, but it is a preview storefront with no trustworthy purchase-to-access path.

### 3.1 [CRITICAL] Three of four hosting passes cannot grant their advertised access

The store sells 24-hour, 3-day, 30-day, and lifetime products (`app/store.tsx:47-52`). Runtime entitlement state is one boolean, `hasMasterPass`, with no product, purchase time, or expiry (`src/store/cosmeticsStore.ts:16-26,87-100`). Entitlement sync checks only RevenueCat's `master` entitlement (`lib/entitlement.ts:24-67`), and the setup doc attaches that entitlement only to the lifetime Master product (`docs/MONETIZATION.md:28-38`).

A user can therefore pay for Deal, Draw, or Shuffle and still receive no hosting access. Restore cannot reconstruct duration either. Do not expose those SKUs until expiry is server-authoritative and tested.

### 3.2 [CRITICAL] Host payment enforcement is cryptographically fake

The client reads `EXPO_PUBLIC_DECKD_MASTER_SECRET` and mints its own HMAC (`lib/entitlement.ts:27-45`). `EXPO_PUBLIC_*` values are embedded in client bundles, despite the file comment claiming the secret is not embedded (`lib/entitlement.ts:1-16`). `hostLobby` computes the token regardless of RevenueCat entitlement (`src/store/lobbyStore.ts:104-132`), and the relay merely compares that token (`server/index.js:104-114`).

If both secrets are set, every app can mint a valid host token. If neither is set, everyone hosts. If only the server is set, nobody hosts. Replace this with server-side RevenueCat receipt/webhook verification and a short-lived, signed host grant.

### 3.3 [CRITICAL] A missing product mapping can charge the wrong item

Purchase lookup falls back to the first available RevenueCat package when the requested ID is not found (`lib/iap.ts:11-20,32-44`). That can turn a tap on £0.99 into another product. Never substitute. Fail closed, show the actual StoreKit package title/price, and require an exact product/package ID match. Displayed prices are hard-coded GBP strings (`app/store.tsx:32-52`) rather than localized store prices.

### 3.4 [MAJOR] Cosmetics are pretend purchases

Locked card backs unlock on long press (`app/store.tsx:208-243`), and locked table themes unlock on one normal tap (`app/store.tsx:257-276`). Neither calls IAP. Ownership is just editable local persisted state (`src/store/cosmeticsStore.ts:64-101`). Preview mode explains the choice internally, but on a public paid surface it makes the catalogue, locks, and prices meaningless.

### 3.5 [MAJOR] The upsell makes promises the entitlement does not fulfil

Master advertises premium felts and exclusive backs (`app/store.tsx:177-198`), but syncing Master only flips a boolean and unlocks no cosmetics (`src/store/cosmeticsStore.ts:79-88`). Home advertises a “Starter Bundle, 50% off” that does not exist in the product list (`components/layers/HomeLayer.tsx:439-450`; `app/store.tsx:47-52`). The lobby says hosting needs Master while preview code deliberately bypasses the gate (`components/layers/LobbyLayer.tsx:70-76,187-194`). Remove fake offers and send a blocked host directly to one honest purchase screen.

### 3.6 [MAJOR] Suit credits do not exist, and adding them now would be silly

“Suits” appear only as a parked AI-generation currency (`docs/DESIGN_PLAN.md:222-243`; `docs/PARKED_IDEAS.md:8-22`). No profile, entitlement, ledger, earn timer, server endpoint, or purchase code implements them. With no account or authoritative ledger, users would lose credits across devices or edit/reset them locally. Keep suits parked until the recipe generator exists and server identity, rate limits, restore, and fraud rules exist.

### 3.7 [NICE] Keep host-pays, simplify everything else

The good idea is “host pays, guests join free” (`docs/MONETIZATION.md:5-16`). Ship one non-consumable lifetime Master SKU at about £14.99 while the library is small, plus free pass-and-play. Add real £1.99 to £2.99 cosmetic packs later. Do not add ads, they poison a shared table and will earn fuck-all at this scale. Do not use credits for hosting. Suits can fund future AI recipe generation only after that feature is real.

## 4. Single-player offline

### 4.1 [MAJOR] There is no user-facing solo mode today

Session modes contain pass, BLE, and online variants, not solo (`src/engine/types.ts:62-68`). Hub player choices are hard-coded to 2 through 6 (`components/layers/HubLayer.tsx:45-46,117-120`). Freeplay technically supports one player (`src/engine/presets.ts:81-92`), but the UI cannot start it and it has no objective. “Solo” is currently absent.

### 4.2 [NICE] Blackjack has the closest thing to a solo foundation

`gameStore` appends a virtual house seat (`src/store/gameStore.ts:116-127`), and the rules provide hit/stick, ace handling, dealer draw-to-17, reveal, and winner resolution (`src/engine/rules.ts:103-217`). Exposing one human plus house is cheap.

It is not polished blackjack yet. The preset explicitly has no betting (`src/engine/presets.ts:119-157`), there is no natural-blackjack treatment, bankroll, round history, replay loop, double, split, or insurance. Today one hand ends the whole session.

### 4.3 [MAJOR] Poker is a dealing/evaluator shell, not poker against bots

There is no bot controller or decision policy. `CHECK`, `CALL`, and `RAISE` all do exactly the same thing, end the turn (`src/engine/rules.ts:329-350,440-451`). `GameState` has a pot field, but no bet/chip events update it (`src/engine/types.ts:82-87`; `src/engine/state.ts:235-248`). Community dealing and hand evaluation work, but there are no blinds, stack sizes, current bet, legal raise sizes, betting-round completion, opponent AI, or side pots.

### 4.4 [MAJOR] Solitaire is documentation, not code

Klondike, FreeCell, Pyramid, and Golf are explicitly deferred (`docs/PARKED_IDEAS.md:24-35`). Existing zones model hands, draw/discard, and one communal row, not tableau columns or foundations (`src/engine/presets.ts:28-54`). A real solitaire mode needs its own state, legal-move selectors, undo, win detection, and board UI.

### 4.5 [MAJOR] Persistence exists, but offline guarantees are uneven

The active event log and sequence persist, then fold back into state on hydration (`src/store/gameStore.ts:355-366`). Web uses localStorage; native uses MMKV, but silently falls back to process memory if MMKV fails (`lib/storage.ts:18-52`). Native assets are bundled and RevenueCat startup is non-blocking (`app/_layout.tsx:36-52`), so an installed native build should launch and resume pass-and-play without network. That still needs airplane-mode and kill/relaunch proof.

The web cold-launch gap remains Finding 2.1. Long solo sessions also need checkpoints because the current TODO admits every launch replays the full event log (`src/store/gameStore.ts:359-365`).

### 4.6 [MAJOR] Concrete build split

Build solo Blackjack first. Do not start poker bots until betting is real.

**DeepSeek, engine/data tasks**

1. Add explicit `solo` mode, stable human/house/bot controller metadata, persisted-state v2 migration, hydration status, corrupt-log recovery, and a guard that never resumes an online guest as the host.
2. Turn blackjack into rounds: natural 21, push, per-player outcome, deterministic dealer policy, “next hand”, win/loss history, and tests for soft aces, busts, dealer ties, persistence, and replay.
3. Add a pure deterministic bot interface and turn runner with intent IDs. Keep delays in orchestration, never inside reducers.
4. Implement heads-up poker before its bot: stacks, blinds, current bet, min-raise, pot, street completion, fold/showdown, then deterministic easy/normal policies. Test complete seeded hands.
5. Implement Klondike as a separate engine slice: stock, waste, seven tableau columns, four foundations, legal moves, draw-one, undo, win detection, deterministic seed, versioned save, and replay tests.

**Luna, mobile UI tasks**

1. Add a clear “Play solo” entry and one-player setup, with Blackjack first and unavailable games honestly labelled.
2. Build a 375px blackjack table with a real dealer zone, hidden hole card, score/outcome sheet, 44px actions, next-hand flow, reduced motion, and VoiceOver labels.
3. Add bot presence and pending-turn feedback, including “thinking”, disabled duplicate actions, reconnect-safe animation cancellation, and no fake timers in engine state.
4. Build the heads-up poker surface only after DeepSeek's betting contract passes: stacks, pot, bet amount, legal action sheet, showdown, and hand history.
5. Build a tap-first Klondike board with drag as an enhancement, selectable source/target, undo, hint, auto-finish, portrait 375px proof, and visible saved-game recovery.

Acceptance for every solo milestone: installed native app launches in airplane mode, starts a fresh game, survives kill/relaunch at three checkpoints, finishes deterministically, and makes zero gameplay network calls.

## Prioritized 10-item action list

1. Implement stable identity, reconnect backoff, room/seat resume tokens, `AppState` handling, and host-disconnect grace.
2. Fix sync correctness: reset cursors per session ID, add ACKs, intent IDs, sequence-gap detection, retries, and second-game/reconnect tests.
3. Fix the disconnect host-view fallback immediately, then send recipient-filtered public/private state instead of the full deck to every guest.
4. Add presence, current-turn disconnect handling, host skip/kick or bot takeover, guest auto-navigation, and host migration or explicit room recovery.
5. Replace the public HMAC shortcut with server-side RevenueCat verification and short-lived host grants.
6. Collapse monetisation to one real lifetime Master SKU, exact package matching, store-sourced localized prices, and no fake cosmetic unlocks or sale banners.
7. Add a versioned service worker/offline fallback, immutable hashed-asset caching, compression, route splitting, font subsetting, and smaller card images.
8. Finish iPhone Safari/native work: `viewport-fit=cover`, dynamic viewport/keyboard handling, universal 44px targets, honest permissions/settings, and physical-device QA.
9. Ship solo Blackjack with the DeepSeek engine tasks and Luna UI tasks, proven in airplane mode and across kill/relaunch.
10. Only then build real heads-up poker AI and Klondike. More cosmetic store work before playable solo content is the wrong priority.
